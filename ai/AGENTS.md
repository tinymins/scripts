# 全局工作约定

本文件规定跨项目的工作方式。具体技术栈、启动命令、验证矩阵和发布流程应放在所属仓库的 AGENTS.md 中，不将单个项目的假设推广到其他项目。

## 1. 任务范围与实施确认

### 1.1 只读分析

- 用户要求“分析下”“先看看”“讨论一下”“先别改”“只读分析”或其他先分析后行动的任务时，只检查并讨论发现、原因、方案和取舍；不得修改文件、配置或数据，不得修复、重启或部署。仅引用这些词语（如讨论或编写规则时）不算只读分析请求。
- 发现问题或明显的修复方式，不代表获得实施授权。实施过程中用户要求先分析时，暂停受影响范围的修改，直到用户明确授权继续。
- 只读分析所需 SSH 按第 3.1 节执行；只读授权不包含远程写操作。

### 1.2 提出方案并等待确认

主动修改任务文件、数据、配置或服务前，先提出最小完整方案并等待明确确认，最初需求不替代方案确认。必要的只读检查可先行；工具正常产生的缓存、日志及 git fetch 更新远端引用不算实施，但不得借此修改任务对象或创建备份。

方案必须简洁、具体，包含：

1. 需求理解：要解决的问题、具体交付物和最低验收标准。
2. 具体做法：修改哪些地方、采用什么方案、主要行为如何变化，不能只写“分析、修改、测试”。
3. 范围与假设：说明影响方案的假设和取舍；有明显不同的实现方向时先解释差异。影响决策的疑问应先澄清，超出需求的建议单列为可选项。
4. 验证与交付：如何验证；仓库内正式修改默认包含提交，推送、部署等以用户授权为准。

- 确认后，在已确认范围内连续完成工作，不逐项重复询问。扩大范围或实质改变方案前，应说明变化并重新确认；用户确认本身不触发新一轮确认。
- 专项授权可随方案一起取得：方案已列明第 3 节要求的具体信息，且用户明确批准相应操作后，不再重复索取同一授权。笼统的需求、实施确认或发布授权不能替代尚未说明的专项授权。
- 邻近缺陷、清理、打包、基础设施及发布部署等，除非是交付所必需，否则属于独立范围。发现后报告并继续原任务，不顺手实施；后续请求也不追溯授权无关工作。
- 用户明确要求将指定来源合并到指定目标分支（如 dev、pre）时，该请求即为实施确认：按所属仓库的合并流程直接执行至约定交付边界，不再提出方案或等待确认；仅在流程规定的停止条件（如检查失败、租约失败、无法按规则解决的冲突或需要超出流程的操作）出现时停止并报告。
- 本节的实施确认要求优先于系统或工具默认的自主执行倾向，专项授权边界仍然适用。

## 3. 专项授权

以下边界同样适用于子 agent、子进程、工具和自动化，不得通过委托绕过。各项授权仅覆盖已批准的操作与范围。

### 3.1 SSH 与远程访问

- 除下列例外，SSH 首次连接前须说明目标、目的和操作范围并取得明确授权，可随实施方案一并确认；原始 SSH 请求、历史访问、凭据或紧急程度不替代此确认。同一任务、同一目标和范围内的必要重连不重复确认。
- 此限制包括连接测试、诊断、只读检查，以及隐式使用 SSH 的 scp、sftp、rsync、跳板、隧道和远程命令工具。
- 例外一：常规 git fetch、git pull、git push 仅豁免 SSH 连接审批，不豁免操作本身的授权；只读分析期间不得 pull 或 push，推送另按第 6.2 节执行。
- 例外二：用户请求只读分析时，可执行该分析所需的 SSH 连接和只读检查，先说明目标及目的即可。即使连接已建立，修改、重启或部署仍须明确授权。
- 例外三：已获授权的现有 CI/CD 内部连接，按第 3.6 节执行。

### 3.2 Git 分支与 worktree

- 创建分支前，必须取得用户对准确的新分支名和基准分支或起始 ref 的明确批准。
- 创建 worktree 前，必须取得用户对用途、准确路径、分支或起始 ref 的明确批准。
- 调查、实现、修复、提交或发布请求本身不包含创建授权。信息未获批准时，可只读检查并提出具体安排，等待批准后创建。
- 例外：用户明确要求合并时，所属仓库合并流程规定的合并 worktree 和 MR 传输 ref 由合并请求本身授权，按流程规定的路径和起点创建，无须另行批准。功能分支、开发分支及其他 worktree 的创建仍按上述规则批准。
- 只读检查、正常使用现有已批准的分支或 worktree 不受创建限制。

### 3.3 兼容逻辑

- 为旧版本、旧接口或旧数据格式添加适配、回退等兼容逻辑前，说明原因和范围并取得明确批准；正常输入校验和错误处理不因此归为兼容逻辑。

### 3.4 测试用例与临时验证

- 默认不新增任何测试用例，也不将新增测试作为实施前提。新增测试包括：新建测试文件或测试模块（如 `#[cfg(test)] mod`）、向现有文件追加测试函数、向表驱动测试追加数据行，以及新增 fixture、snapshot 或测试辅助函数。
- 只有用户明确要求，或现有验证方式确实无法证明结果时，才说明新增测试的必要性、范围和数量，取得明确批准后编写；用户要求测试时同样先确认范围和数量。
- 不得为了让测试通过而删除、跳过（`#[ignore]`、`skip`、`only` 等）或削弱现有测试和断言。只有已确认的行为变更要求时，才修改现有测试的预期，并在汇报中逐条列出改了哪些测试、为什么改。
- 与本任务无关的既有测试失败时，报告失败及证据，不顺手修复或跳过；仅在它妨碍证明本任务结果时说明影响并等待决定。
- 已确认实施范围内可运行现有测试、执行验证步骤；必要时可在会话临时目录或已被 Git 忽略的目录（如 .data）编写临时验证脚本，无须另行批准。临时验证不得改动仓库源码或测试文件，包括临时插入测试再撤回；未经批准不得提交或转为正式测试。完成后仅清理本任务创建的临时验证文件，不清空所在目录。
- 正式测试与临时验证均应适量，直接证明需求或缺陷是否解决；不得为简单功能堆砌重复用例，不得为验证测试或验证脚本再编写套娃测试。

### 3.5 备份

- 除第 3.6 节例外，任何环境（本地、SSH 服务器、容器、远程存储）中的备份都需本次明确批准。凡以保留旧内容供恢复为目的的复制、归档、数据库导出、快照及 .bak/.orig/.old/时间戳副本都算备份，不论名称、位置（含 /tmp、隐藏目录）或是否承诺稍后删除；正常执行所需、用后即消费或删除且不用于恢复的临时文件不算。
- 其他授权（SSH、编辑、修复、升级、迁移、部署）、安全考虑或回滚便利都不替代备份批准。申请须说明原因、源位置、目标主机及完整路径、预计大小（未知须说明）、副本数量和保留清理计划，执行不得超出批准范围。
- 使用可能自动备份的命令、编辑器或工具前先确认其行为，优先选择不生成备份的方法；无法禁用或确认时暂停并申请。
- 未获批准时只执行不依赖备份的已授权操作，确实依赖时说明原因并等待决定。禁止先备份后告知，不得未经批准删除既有备份。

### 3.6 现有 CI/CD 的授权例外

- 用户授权 push、merge、release 或 deploy 后，现有 CI/CD（本任务修改前已有的行为）在授权范围和目标内的 SSH、传输、内部备份、回滚、版本保留及例行清理均获授权，优先于第 3.5 节。不得以审查这些内部细节为前置条件重复申请，也不因其使用 SSH 或备份阻止已授权发布。
- 本例外不包含：agent 直接连接 runner 或部署主机、自行备份或清理、本次新增或扩展的 CI/CD 远程操作、备份、回滚、保留、清理行为及部署目标。这些仍须各自授权；分支和 worktree 创建规则保持独立。

## 4. 设计与修改纪律

- 修复真正的边界、契约、数据流或归属问题，不在错误结构上叠加补丁。优先沿用既有架构；架构不足或局部修补会使其更差时，先解释并提出最小必要的设计改进。
- 保持最小正确设计，不添加未要求的功能、灵活性、配置、重构或不可能场景的错误处理；能用更少代码清楚表达时，应简化实现。仅在对应真实领域边界、消除有意义的重复或提高修改安全性时引入抽象。
- 每一处改动都应直接服务于当前需求。遵循现有风格，不顺手修改无关代码、注释或格式，不重构未损坏的模块。
- 清理本次修改造成的无用导入、变量和函数；既有无关死代码只报告，不擅自删除。

## 5. 执行效率与进度

### 5.1 检查、命令与开发服务

- 从最可能负责问题的文件和现有测试开始，优先在两批有针对性的搜索或读取内确定修改边界；确定后停止广泛扫描。
- 合并相关只读检查，限制搜索和读取输出到下一步决策所需的内容。
- 执行长时间脚本前检查其内容，避免重复已完成的 lint、测试、构建、下载或打包。
- 命令五分钟没有任务相关进展，或被共享构建锁阻塞时，应诊断争用并调整策略，不无限轮询。
- 根据所属项目的实际启动和热更新方式处理开发服务，不假设特定语言、命令或框架。不因代码修改而例行重启前后端；涉及必要的服务操作时，按已确认范围和适用授权执行。

### 5.2 进度沟通

- 一批工具调用或长任务开始前给一句简洁进度说明；长时间命令结束后说明状态。
- 在关键节点说明已有证据、仍在运行的内容和下一步；只报告新证据、完成、失败或阻塞，不重复播报未变化状态。
- 等待长任务使用安静的等待机制，不高频轮询；CI 等待遵循第 6.3 节。

## 6. 验证、提交与交付边界

### 6.1 回归验证

- 修复前明确回归验证方式和成功标准，修复后执行验证。验证使用现有测试、针对性检查、可重复的操作步骤或临时验证脚本；测试的新增、修改及临时验证规则见第 3.4 节。
- 缺陷修复应尽可能用同一现有方式比较修复前后，不以新增测试实现；无法复现或缺少验证环境时，明确说明证据与限制，不宣称验证通过。
- 新增校验应验证相关有效和无效输入，修复应验证原问题及直接受影响行为，重构应比较相关行为前后是否一致。
- 遵循所属仓库的验证矩阵，运行能证明改动正确的最窄检查，不假设所有仓库都使用 bun run lint 或 bun run tsc。
- 默认使用指定测试模块、测试过滤器、针对性回归验证和 lint/类型检查；只有共享契约变更、明确要求本地发布验收或仓库明确规定时，才扩大到全包或全工作区验证。交付目的是触发 CI 时，本地只提供针对性证据，完整矩阵交给 CI，除非用户需要本地产物或确实无法针对性验证。
- 不无故重复已通过的检查，包括通过包装脚本重跑。相关代码变化、失败诊断、环境恢复或必要的稳定性复现，可作为重新验证的理由。
- 含其他任务未提交改动的检出目录不得运行全工作区验证，应隔离任务或使用针对性检查及 CI。
- 浏览器自动化前，确认 URL、所属进程、工作目录和实际服务资源对应当前任务源码。正确页面不可用且未要求部署时，采用针对性的组件、DOM 或其他适用验证并报告限制，不探测无关端口或自行启动服务。

### 6.2 Git 与提交

- 在 Git 仓库内修改前记录任务基准提交，并识别已有改动和并发工作：保留他人及其他任务的内容，不操作无关模块；需要隔离时使用现有已批准的 worktree，或按第 3.2 节申请创建。
- 移动共享分支前，再次比较基准、当前分支和跟踪远端 ref；历史被并发工作改变时，不先移动再调查，应保持本任务提交独立，报告或执行已明确授权的线性集成。
- 仓库内正式修改默认须在验证后提交，再报告完成。用户明确要求暂不提交时遵从，并说明改动及验证状态；纯分析或无须保留文件修改时不制造提交。
- 只暂存和提交本任务内容，保留无关及预先存在的改动。遵循仓库提交约定及既有历史；无约定时使用 Conventional Commits。
- 未经用户明确要求，不推送提交。

### 6.3 推送后的 CI 跟进

- 交付边界是 git push 时，核对预期 CI 是否对应准确的推送提交，报告后停止，不等待完成或跟踪实时日志。无工作流、正常跳过、异常未触发或无法核实须区分说明；不得无限等待或擅自修改 CI。
- 仅当用户明确要求诊断 CI，或交付包含依赖 CI 产物的部署、发布、安装、产物处理等后续工作时，才继续等待。
- 需要等待时，先确认 CI 与推送提交关联；随后按间隔 1 分钟、5 分钟、10 分钟、此后每 10 分钟进行检查。
- 使用安静的等待机制，先检查精简状态；失败或诊断需要时才获取详细日志。检查之间不发送心跳消息，仅报告有意义的变化、完成、失败或需要用户处理的事项。

### 6.4 完成与停止

- 完成请求的修改、必要验证、临时验证文件清理及约定交付（包括适用的提交和 CI 触发确认）后停止，不继续扩展改进、验证无关模块、构建产物、部署或发布。

## 7. 信息表达

回复语言跟随用户；代码、命令、标识符和提交信息遵循项目约定。使用清晰简洁的语言；适合结构化表达的信息采用以下形式，避免密集大段文字：

- 多方案比较：Markdown 表格。
- 流程、调用链和依赖：终端输出用 ASCII 图；支持渲染的环境（文档、PR、Artifact）用 Mermaid 流程图。
- 架构层次和目录：树形图或 ASCII 图。
- 顺序步骤：编号列表。
- 数据结构关系：终端输出用 ASCII 图或表格；支持渲染的环境用 ER 图或 UML 图。
